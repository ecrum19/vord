This draft defines a practical usage profile for https://w3id.org/vord# (VoRD) so SPARQL endpoint maintainers can publish machine-readable operational limits in SPARQL Service Description documents. It prioritizes the most important limits to expose first and specifies how those limits are represented.

This is an unofficial proposal.

Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL are to be interpreted as described in RFC 2119 and RFC 8174.

service description
An RDF description of a SPARQL endpoint using SPARQL Service Description.
quantitative limit
A limit expressed with a numeric threshold, typically using vord:metric and vord:maxValue.
capability limit
A boolean support statement, currently represented by vord:FederatedQueryLimit with vord:federationSupported.

Conformance

A conforming VoRD publisher is an implementation that publishes endpoint limits in a service description and satisfies the normative requirements in this document.

The following prefixes are used throughout this document:

PREFIX sd:   <http://www.w3.org/ns/sparql-service-description#>
PREFIX vord: <https://w3id.org/vord#>
PREFIX xsd:  <http://www.w3.org/2001/XMLSchema#>

Publishing Model

A service description resource of type sd:Service MUST relate to one or more limit resources using vord:hasLimit. Because vord:hasLimit is a subproperty of sd:feature, consumers can discover VoRD limits through either property.

Every quantitative limit resource MUST include:

  • a vord:Limit and a concrete VoRD limit class.
  • vord:metric and vord:maxValue.
  • vord:hasScope, vord:enforcement, and vord:hardLimit.

A federation capability limit MUST include vord:federationSupported (boolean) and MUST NOT use numeric federation metrics.

Priority Profile for Maintainers

This section defines which limits are most important to publish first.

Priority Limit class Why it matters Minimum required fields
MUST vord:RateLimit Prevents unexpected 429 behavior for clients. vord:metric (vord:requestsPerWindow or vord:requestsPerDay), vord:maxValue, vord:windowDuration, vord:hasScope, vord:enforcement, vord:hardLimit.
MUST vord:TimeoutLimit Critical for query planning and timeout retries. vord:metric (typically vord:executionSeconds), vord:maxValue, vord:hasScope, vord:enforcement, vord:hardLimit.
MUST vord:ResultSizeLimit Prevents client-side parsing/memory failures. vord:metric (vord:resultRows or vord:resultBytes), vord:maxValue, vord:hasScope, vord:enforcement, vord:hardLimit.
MUST vord:FederatedQueryLimit Lets clients know whether SERVICE is supported. vord:federationSupported (boolean), vord:hasScope, vord:enforcement, vord:hardLimit.
SHOULD vord:ConnectionNumberLimit Helps clients avoid overload during concurrency bursts. vord:metric, vord:maxValue, vord:hasScope, vord:enforcement, vord:hardLimit.
SHOULD vord:QuotaLimit Improves predictability of daily/periodic API usage. vord:metric (typically vord:requestsPerDay), vord:maxValue, vord:windowDuration, vord:hasScope, vord:enforcement, vord:hardLimit.
MAY vord:QuerySizeLimit, vord:ServerLoadLimit, vord:CostModelLimit Useful advanced constraints for power users and optimizers. Use standard quantitative pattern; include vord:costModel for cost-based limits.

How to Include Limits in Service Descriptions

Endpoint maintainers SHOULD publish a dedicated service description IRI and include all active limits in that description.

Minimal mandatory set example

@prefix ex:   <https://example.org/sparql/> .
@prefix sd:   <http://www.w3.org/ns/sparql-service-description#> .
@prefix vord: <https://w3id.org/vord#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

ex:service a sd:Service ;
  sd:endpoint <https://example.org/sparql> ;
  vord:hasLimit ex:rate, ex:timeout, ex:resultSize, ex:federationSupport .

ex:rate a vord:Limit, vord:RateLimit ;
  vord:metric vord:requestsPerWindow ;
  vord:maxValue "60"^^xsd:decimal ;
  vord:windowDuration "PT1M"^^xsd:duration ;
  vord:hasScope vord:PerClientIP ;
  vord:enforcement vord:RejectRequest ;
  vord:hardLimit true ;
  vord:returnsStatusCode 429 .

ex:timeout a vord:Limit, vord:TimeoutLimit ;
  vord:metric vord:executionSeconds ;
  vord:maxValue "30"^^xsd:decimal ;
  vord:hasScope vord:PerRequest ;
  vord:enforcement vord:RejectRequest ;
  vord:hardLimit true .

ex:resultSize a vord:Limit, vord:ResultSizeLimit ;
  vord:metric vord:resultBytes ;
  vord:maxValue "10000000"^^xsd:decimal ;
  vord:hasScope vord:PerRequest ;
  vord:enforcement vord:TruncateResult ;
  vord:hardLimit true .

ex:federationSupport a vord:Limit, vord:FederatedQueryLimit ;
  vord:federationSupported true ;
  vord:hasScope vord:GlobalScope ;
  vord:enforcement vord:RejectRequest ;
  vord:hardLimit true .

Publisher guidance

  • Publishers MUST keep VoRD statements synchronized with runtime behavior. If implementation policies change, service descriptions MUST be updated.
  • Publishers SHOULD include vord:returnsStatusCode where applicable (for example 429 or 503).
  • Publishers SHOULD include vord:retryAfterHint for throttling behavior to improve client backoff behavior.
  • Publishers MAY include vord:signalsHeader when limit state is surfaced through HTTP headers.

Security and Privacy Considerations

Publishing precise operational limits can help clients and can also aid abusive traffic shaping. Deployments may choose coarser values while remaining truthful about effective enforcement.
