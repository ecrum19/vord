This document defines a practical usage specification for https://w3id.org/vord# (VoRD), a vocabulary for describing operational restrictions of SPARQL services. It is written primarily for SPARQL endpoint maintainers who need to publish rate limits, result-size limits, timeouts, quotas, concurrency limits, usage budgets priced by a cost model, requirements to identify the client, penalties such as temporary blocks, load-shedding behavior, and related HTTP signals in a machine-readable form that users and query engines can discover.

VoRD extends SPARQL Service Description by treating endpoint restrictions as service features linked from an sd:Service. The goal of this specification is to make those descriptions predictable enough that automated clients can choose endpoints, plan query batches, avoid known limits, and respond correctly when a limit is reached.

This is an unofficial draft. It is a vocabulary usage specification, not the definitive ontology publication for the VoRD namespace. Normative requirements in this document are intended to define a publishable maintainer profile for VoRD data.

Introduction

Public SPARQL endpoints commonly enforce operational limits: requests per minute, execution deadlines, maximum result sizes, per-client quotas, concurrency ceilings, or temporary throttling under load. Some services go further: they meter usage in cost units rather than requests, require every client to identify itself with contact information, or block clients that violate a limit for a period of time. These limits are often documented only in human-readable prose. That is not sufficient for federated query engines, crawlers, batch clients, or monitoring tools that need to adapt before sending work to an endpoint.

SPARQL Service Description already defines a discovery mechanism and a vocabulary for describing SPARQL services. In particular, a service can be represented as sd:Service, linked to its endpoint with sd:endpoint, and linked to features with sd:feature [[SPARQL11-SERVICE-DESCRIPTION]]. VoRD reuses that model by defining vord:hasRestriction as a service-to-restriction property and as a subproperty of sd:feature.

The examples in this specification use Turtle, a compact concrete syntax for RDF graphs [[TURTLE]]. The validation profile is expressed in SHACL, which is a language for describing and validating RDF graphs [[SHACL]].

Scope

This specification covers how to publish VoRD descriptions for SPARQL endpoints. It does not define server-side rate-limiting algorithms, require a particular SPARQL implementation, or require endpoint operators to reveal sensitive internal capacity data. Where exact internal values are operationally sensitive, publishers can disclose conservative public thresholds, advisory limits, or load-dependent behavior.

A VoRD description is about operational behavior visible to clients. It should describe the effective limit that a well-behaved client can rely on, rather than every internal limiter, proxy, firewall, or scheduler rule that may contribute to enforcement.

Terminology

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals, as shown here.

VoRD publisher
An endpoint maintainer, documentation maintainer, or automated deployment process that publishes VoRD RDF for a SPARQL service.
VoRD consumer
A user agent, query engine, crawler, client library, catalog, or monitoring system that reads VoRD RDF to understand endpoint restrictions.
restriction
A resource typed vord:Restriction that states a measurable operational threshold and the way the endpoint enforces that threshold.
hard restriction
A restriction whose threshold is intended to be strictly enforced. It is represented with vord:hardRestriction true.
advisory restriction
A published threshold that is approximate, load-dependent, or guidance-only. It is represented with vord:hardRestriction false.

Conformance

A conforming VoRD publisher satisfies all normative requirements in this document that are addressed to publishers. A conforming VoRD consumer satisfies all normative requirements in this document that are addressed to consumers.

A VoRD publisher MUST publish RDF that conforms to the data model in and the maintainer profile in . A VoRD publisher SHOULD validate the published RDF with the SHACL shapes summarized in before deployment.

A VoRD consumer MUST NOT assume that a missing restriction means that no corresponding operational limit exists. Missing VoRD data only means that the publisher did not advertise that limit in the VoRD description.

Publishing Model

Discovery

A VoRD publisher SHOULD include VoRD triples in the SPARQL service description returned by dereferencing the endpoint IRI with HTTP GET and no query parameters. This follows the SPARQL Service Description discovery pattern, which expects an RDF service description at the endpoint and recommends content negotiation for RDF representations [[SPARQL11-SERVICE-DESCRIPTION]].

A VoRD publisher MAY also publish the same VoRD graph at a documentation URL, dataset catalog URL, or VoID/DCAT metadata URL, but that alternative publication SHOULD NOT replace service-description discovery unless endpoint-level discovery is impossible.

Core graph pattern

A VoRD service description MUST include an sd:Service resource with an sd:endpoint IRI. The service resource MUST link to one or more restrictions using vord:hasRestriction. 

@prefix sd:   <http://www.w3.org/ns/sparql-service-description#> .
@prefix vord: <https://w3id.org/vord#> .

<https://example.org/sparql#service> a sd:Service ;
  sd:endpoint <https://example.org/sparql> ;
  vord:hasRestriction <https://example.org/sparql#rateLimit> .

<https://example.org/sparql#rateLimit> a vord:Restriction, vord:RateRestriction .

Each restriction MUST be typed as vord:Restriction and as exactly one standard restriction subclass from VoRD, unless it is an extension restriction as described in .

Restriction identifiers

Restriction resources SHOULD have stable IRIs. Stable IRIs make it possible for documentation, monitoring systems, cached service descriptions, and issue reports to refer to the same operational policy over time. Blank nodes MAY be used for temporary or generated descriptions, but they are not recommended for public endpoint metadata.

Maintainer Restriction Profile

This section defines the minimum properties that make a restriction actionable for users and query engines.

Common requirements

Each standard quantitative VoRD restriction MUST include the following properties exactly once:

  • vord:metric, identifying the measured quantity.
  • vord:maxValue, an xsd:integer threshold.
  • vord:hasScope, identifying the subject of enforcement.
  • vord:enforcement, identifying the action taken when the threshold is reached.
  • vord:hardRestriction, an xsd:boolean indicating whether the threshold is strict.

A vord:IdentificationRestriction is a requirement rather than a threshold. It MUST include exactly one vord:identificationHeader, exactly one vord:identificationFormat, and exactly one vord:hasScope, vord:enforcement, and vord:hardRestriction. It does not need vord:metric or vord:maxValue.

A vord:RequestMethodRestriction is a requirement too. It MUST include at least one vord:allowedRequestMethod, one for every way of sending a query that the endpoint accepts, and exactly one vord:hasScope, vord:enforcement, and vord:hardRestriction. It does not need vord:metric or vord:maxValue.

A restriction whose violations lead to a temporary block of the client SHOULD state vord:penaltyThreshold and vord:penaltyDuration. If it states vord:penaltyThreshold, it MUST also state vord:penaltyDuration. If the endpoint does not publish the threshold or the duration of its blocks, the restriction SHOULD state vord:penalized true instead.

If the unit is not obvious from the metric, the restriction MUST include vord:unit. Publishers SHOULD use QUDT unit IRIs such as unit:COUNT, unit:SEC, unit:PERCENT, and unit:ONE for dimensionless cost scores [[QUDT-UNITS]].

Publishers SHOULD include vord:returnsStatusCode and vord:httpSignalHeader when clients can use HTTP status codes or headers to respond to the restriction. For rate-limit rejections, 429 is the HTTP status code for too many requests and may be accompanied by a Retry-After header [[RFC6585]]. HTTP semantics, including status code and header behavior, are defined by RFC 9110 [[RFC9110]].

Priority profile for endpoint maintainers

A public endpoint that wants basic machine-readability MUST publish the restrictions that are both enforced and externally meaningful. The following priority profile is recommended for incremental adoption.

Scope guidance

The scope tells clients who or what is counted. A publisher MUST choose the most specific accurate scope. For example, use vord:PerClientIP for an IP-based limiter, vord:PerClientIdentity for a limiter that counts each combination of User-Agent and IP address (or of the header that a vord:IdentificationRestriction names and IP address), vord:PerAPIKey for a key-based limiter, vord:PerUser for authenticated user identity, vord:PerRequest for a single query execution, and vord:GlobalScope for a limit shared by all traffic.

If the limiter uses a different identity function, such as API key plus IP address, the publisher MAY mint a custom scope IRI. Custom scopes MUST be typed vord:Scope and SHOULD have skos:prefLabel and dcterms:description.

Enforcement guidance

The enforcement mode tells clients what happens at the threshold. Publishers MUST choose the enforcement mode that describes the externally visible behavior. Use vord:RejectRequest when requests fail at or above the threshold, vord:TruncateResult when partial results are returned, vord:QueueRequest when requests are delayed, vord:ThrottleResponse when processing or delivery is slowed, and vord:DegradeQuality when the service responds with reduced quality or partial capability.

Freshness and operational truth

A VoRD publisher MUST keep machine-readable restrictions synchronized with the effective public policy. If a limit changes, the VoRD description SHOULD be updated in the same deployment or documentation release as the actual limiter. Publishers SHOULD use dcterms:modified or another metadata property on the service description graph to help consumers assess freshness.

A publisher MUST set vord:hardRestriction false when a threshold is only a recommendation, when it is load-dependent, or when it may vary without prior notice. Consumers SHOULD treat advisory restrictions as planning hints rather than guaranteed behavior.

Implementation Guidance for SPARQL Endpoint Maintainers

Recommended implementation steps

  1. Inventory all externally meaningful limits: rate windows, result truncation, query timeout, concurrency, quotas, load shedding, cost-based admission, and the ways of sending a query that are refused.
  2. Decide the public service IRI and make sure it has an sd:endpoint triple.
  3. Create one restriction resource per independent limit. Do not collapse unrelated limits into one resource.
  4. Use standard VoRD metrics, scopes, and enforcement modes whenever they match the deployed behavior.
  5. Add units, windows, HTTP status codes, and retry hints so clients can act without scraping prose documentation.
  6. Validate the graph with SHACL, publish it through service-description discovery, and monitor it for drift against production configuration.

HTTP signals

A VoRD publisher SHOULD align published HTTP signals with actual endpoint behavior. For a rate limiter that returns 429 and Retry-After, publish both vord:returnsStatusCode "429"^^xsd:integer and vord:httpSignalHeader http:retry-after. If the server may also return 503 during backend overload, publish that as a separate load or concurrency restriction rather than overloading the rate restriction.

Some headers that endpoints use to signal restrictions, such as X-RateLimit-Remaining or X-SQL-State, are not defined by the HTTP Vocabulary in RDF [[HTTP-IN-RDF10]]. Publishers MAY mint IRIs for such headers. A minted header IRI SHOULD be typed httpv:HeaderName, where httpv: is http://www.w3.org/2011/http#, and SHOULD have an rdfs:label with the header name. Consumers take the local name of a header IRI, after the last # or /, as the case-insensitive header name. 

@prefix ex: <https://example.org/sparql/> .
@prefix httpv: <http://www.w3.org/2011/http#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:x-ratelimit-remaining a httpv:HeaderName ;
  rdfs:label "X-RateLimit-Remaining" .

Result truncation

When a result-size limit causes partial results, the restriction MUST use vord:TruncateResult. When a result-size limit rejects the request before execution or fails the query, use vord:RejectRequest. Publishers SHOULD document, using dcterms:description, whether truncation is visible through a warning, a status code, or response metadata.

Dynamic or load-dependent limits

For dynamic server behavior, publish the stable public policy rather than a rapidly changing internal metric. If an endpoint degrades under load without a fixed threshold, use vord:ServerLoadRestriction, set vord:hardRestriction false, and describe the behavior in prose with dcterms:description.

Usage budgets

Some services meter usage in cost units rather than in requests: each request costs a number of units that depends on its kind or size, and a client may spend a budget of units per period. OpenAlex, for example, gives each API key a daily budget, prices requests by type, and reports the remaining budget in response headers [[OPENALEX-RATE-LIMITS]]. GitHub's GraphQL API charges points per query from a budget per hour [[GITHUB-GRAPHQL-LIMITS]], and Shopify's GraphQL Admin API uses a bucket of points that refills at a fixed rate [[SHOPIFY-GRAPHQL-LIMITS]].

A VoRD publisher SHOULD describe such a budget as a vord:CostModelRestriction with the metric vord:costUnitsPerWindow. vord:maxValue is the number of units per vord:windowDuration, and vord:burstValue, if present, is the number of units that a client can spend at once. The restriction MUST name its cost model with vord:costModel, and the cost model SHOULD explain with dcterms:description how much a request costs, so that clients can anticipate expensive requests.

Because clients cannot always predict the cost of a request, a publisher SHOULD report the remaining budget in a response header, such as X-RateLimit-Remaining, and name that header with vord:httpSignalHeader. When the budget is spent, the endpoint SHOULD reject requests with 429 and a Retry-After header, and publish that status code with vord:returnsStatusCode. The IETF RateLimit and RateLimit-Policy header fields are a standards-track alternative for reporting the budget [[RATELIMIT-HEADERS]].

Processing-time budgets and error limits

Some services limit how much processing time and how many failed requests a client may cause, rather than how many requests it sends. The Wikidata Query Service, for example, gives each client, identified by its User-Agent and IP address together, 60 seconds of processing time per 60 seconds and 30 error queries per minute. Clients over these limits get 429 with Retry-After, and clients that ignore these responses can be banned temporarily [[WDQS-USER-MANUAL]].

A VoRD publisher SHOULD describe a budget of processing time as a vord:QuotaRestriction with the metric vord:evaluationTimePerWindow: vord:maxValue seconds of evaluation time, summed over the requests of the scope, per vord:windowDuration, which is required. The metric vord:evaluationTime remains the time of a single request, for vord:ResponseTimeRestriction. A limit on failed requests SHOULD be described as a vord:RateRestriction with the metric vord:failedRequestsPerWindow. The endpoint decides which requests count as failed; a publisher SHOULD explain this in dcterms:description when it is more specific than requests answered with an error.

Clients can only measure response times, which include network and queueing time, so a client that tracks a processing-time budget with its own response times stays within it. Clients MUST NOT treat a restriction with either of these metrics as a limit on the number of requests they send.

Client identification

Some services require every request to identify the client and a way to reach its operator. Wikimedia's User-Agent policy, for example, asks for a User-Agent that names the client and gives an email address, a website, or a wiki user, and requests without one can be refused with 403 [[WIKIMEDIA-USER-AGENT-POLICY]].

A VoRD publisher SHOULD describe such a requirement with a vord:IdentificationRestriction. It names the request header that must carry the identification with vord:identificationHeader, and the expected content with vord:identificationFormat:

  • http:from with vord:EmailAddress: an email address at which the operator can be reached, as the HTTP From header defines it [[RFC9110]] (section 10.1.2).
  • http:user-agent with vord:ProductWithContact: a product identifier followed by a comment with contact information, such as ExampleBot/1.0 (https://example.org/bot; bot@example.org).

The service description itself MUST NOT require identification, so that clients can learn the requirement before they send their first query. When other limits are counted per identity, they SHOULD use the scope vord:PerUser; the identification is then expected to stay the same for a client.

Request methods

The SPARQL protocol defines three ways of sending a query: in the query string of a GET request, URL-encoded in the body of a POST request, and as the body of a POST request [[SPARQL11-PROTOCOL]] (section 2.1). Some endpoints, or gateways in front of them, accept only some of these. Bgee's endpoint, for example, answered queries sent with GET from a benchmark client on 27 November 2026, but refused both kinds of POST with 403; to the POST with the query as its body, a bot check in front of the endpoint answered with its challenge. Clients that send their longer queries by POST, as many do, then fail on exactly those queries.

A VoRD publisher SHOULD describe such a requirement with a vord:RequestMethodRestriction that lists every accepted way with vord:allowedRequestMethod: vord:QueryViaGet, vord:QueryViaUrlEncodedPost, or vord:QueryViaDirectPost. Ways that are not listed are refused. The status code of the refusal, such as 403 or 405, SHOULD be published with vord:returnsStatusCode. A 405 response names the accepted HTTP methods in its Allow header [[RFC9110]], but only after a refused request, and it cannot tell the two kinds of POST apart.

A query via GET carries the query in the request URL. If the endpoint, or a gateway in front of it, limits the length of request URLs, the publisher SHOULD state the limit in dcterms:description, so that clients know how long a query they can send.

Penalties and temporary blocks

Some endpoints block clients that keep violating a restriction, for example with a firewall rule in the style of fail2ban [[FAIL2BAN]]. A VoRD publisher SHOULD state such a penalty on the restriction whose violations trigger it: vord:penaltyThreshold is the number of violations within vord:penaltyDuration after which the client is blocked, and vord:penaltyDuration is how long the block lasts. A threshold of 1 means zero tolerance: the first violation is penalized. The status code that blocked requests receive, such as 403, SHOULD be published with vord:returnsStatusCode.

Some endpoints block clients that keep violating a restriction without publishing the threshold or the length of the block. A publisher SHOULD then state vord:penalized true on the restriction, so that clients know that ignoring its rejections risks a block. A restriction with vord:penaltyThreshold is penalized, so vord:penalized MUST NOT be false on it.

Limits without errors and degraded answers

Not every restriction produces an error. When an endpoint delays requests over a limit instead of rejecting them, as a tarpit or slow-down middleware does, the restriction MUST use vord:ThrottleResponse. Clients then cannot detect the limit from status codes, so publishing it is the only way to make it known.

When an endpoint answers with reduced quality under load, for example a partial or empty result after an internal time limit, as Virtuoso's anytime queries do, the restriction MUST use vord:DegradeQuality. If such answers are marked by a response header, such as X-SQL-State, the publisher SHOULD name it with vord:httpSignalHeader, and the status code of degraded answers, typically 200, with vord:returnsStatusCode.

Shared limits

A limit with scope vord:GlobalScope is shared by all users of the endpoint: a client only gets what the other users leave. The publisher SHOULD still set vord:hardRestriction true when the shared ceiling is strictly enforced, even though the share that one client can use varies over time. Publishers SHOULD publish a Retry-After signal for shared limits, because clients cannot predict when capacity becomes free.

Extensions

Publishers MAY mint extension metrics, scopes, cost models, and restriction subclasses when the standard VoRD terms do not precisely describe deployed behavior. Extension metrics MUST be typed vord:Metric. Extension scopes MUST be typed vord:Scope. Extension restriction classes SHOULD be declared as subclasses of vord:Restriction.

Extension terms SHOULD include human-readable labels and descriptions. Consumers that do not recognize an extension term SHOULD still process the common VoRD properties on the restriction resource.

Consumer Guidance

VoRD consumers can discover restrictions by querying a service description graph for vord:hasRestriction. The following query returns the core fields that a query engine usually needs for scheduling and endpoint selection. 

PREFIX sd:   <http://www.w3.org/ns/sparql-service-description#>
PREFIX vord: <https://w3id.org/vord#>

SELECT ?endpoint ?restriction ?restrictionType ?metric ?maxValue
       ?unit ?windowDuration ?burstValue ?scope ?enforcement ?hardRestriction
       ?penaltyThreshold ?penaltyDuration ?penalized
       ?identificationHeader ?identificationFormat ?allowedRequestMethod
WHERE {
  ?service a sd:Service ;
           sd:endpoint ?endpoint ;
           vord:hasRestriction ?restriction .
  ?restriction a vord:Restriction ;
               a ?restrictionType ;
               vord:hasScope ?scope ;
               vord:enforcement ?enforcement ;
               vord:hardRestriction ?hardRestriction .
  FILTER(?restrictionType != vord:Restriction)
  # Identification and request-method restrictions have no metric or maximum value.
  OPTIONAL { ?restriction vord:metric ?metric . }
  OPTIONAL { ?restriction vord:maxValue ?maxValue . }
  OPTIONAL { ?restriction vord:unit ?unit . }
  OPTIONAL { ?restriction vord:windowDuration ?windowDuration . }
  OPTIONAL { ?restriction vord:burstValue ?burstValue . }
  OPTIONAL { ?restriction vord:penaltyThreshold ?penaltyThreshold . }
  OPTIONAL { ?restriction vord:penaltyDuration ?penaltyDuration . }
  OPTIONAL { ?restriction vord:penalized ?penalized . }
  OPTIONAL { ?restriction vord:identificationHeader ?identificationHeader . }
  OPTIONAL { ?restriction vord:identificationFormat ?identificationFormat . }
  # One row for every accepted way of sending a query.
  OPTIONAL { ?restriction vord:allowedRequestMethod ?allowedRequestMethod . }
}
ORDER BY ?endpoint ?restriction

Consumers should use vord:hardRestriction to distinguish strict limits from hints, should respect vord:retryAfterHint and HTTP Retry-After signals where present, and should fall back to conservative defaults when a service description is missing or incomplete.

The newer restriction kinds call for specific client behavior:

  • Identification. Consumers should send identification only to endpoints whose description requires it, in the header and format that the description names. Contact details should not be broadcast to every endpoint.
  • Request methods. Consumers should send their queries in one of the ways that vord:allowedRequestMethod lists, for example with GET when POST is refused, rather than learn the restriction from a refused request. A query via GET has to fit in the request URL, so consumers should keep such queries short, for example by sending fewer bindings per query.
  • Usage budgets. Consumers should expect the cost of requests to vary, track the remaining budget from the header named by vord:httpSignalHeader, and pace their requests so that the budget refills, rather than spending it in a burst.
  • Processing-time budgets and error limits. Consumers should sum the response times of their requests per window and pause when the budget of vord:evaluationTimePerWindow is spent, and should count their failed requests against vord:failedRequestsPerWindow. They should not read either as a limit on the number of requests.
  • Penalties. For a restriction with a penalty, consumers should never risk a violation, and should not retry blocked requests while the block of vord:penaltyDuration lasts: retries cannot succeed and may extend the block. For a restriction that is only vord:penalized, they should treat each rejection as final until its Retry-After has passed.
  • Degraded answers. Consumers should treat answers to a restriction with vord:DegradeQuality that carry its signal header as possibly incomplete, even when their status code is 200.

Strict endpoints

This example describes eight endpoints, each with a stricter pattern than a simple rate limit. Each pattern follows a mechanism that real services use; the values are illustrative.

  1. Usage budget: 600 cost units per minute, of which at most 200 can be spent at once, priced by a described cost model, with the remaining budget in X-RateLimit-Remaining.
  2. Identification in the User-Agent: every request must carry a User-Agent with contact information, and the rate limit is counted per identity.
  3. Identification in the From header: every request must carry an email address in From.
  4. Zero tolerance: the first request over 10 per second blocks the client for 10 minutes.
  5. Tarpit: requests over 100 per 10 seconds are delayed, never rejected.
  6. Degraded answers: a request that arrives while three requests of the same client are running gets a partial, possibly empty, answer, marked with X-SQL-State.
  7. Shared limit: all users share 20 requests per second.
  8. Reverse-proxy queue: requests over 10 per second are queued, and rejected with 503 without Retry-After once the queue is full, as nginx's limit_req does [[NGINX-RATE-LIMITING]].

# Strict restrictions, one endpoint per pattern. Each pattern follows a mechanism that real services use;
# the values are illustrative. A client that ignores these restrictions fails in a different way at each endpoint:
# it runs out of budget, is rejected for lack of identification, is banned, is slowed down without any error,
# receives silently empty answers, or competes with other users for a shared limit.

# Headers that the HTTP Vocabulary in RDF does not define get their own IRIs.
ex:x-ratelimit-remaining a httpv:HeaderName ;
  rdfs:label "X-RateLimit-Remaining" .

ex:x-sql-state a httpv:HeaderName ;
  rdfs:label "X-SQL-State" .

# 1. A usage budget in cost units, as OpenAlex, GitHub's GraphQL API and Shopify's GraphQL Admin API meter usage:
#    600 units per minute, of which at most 200 can be spent at once. The remaining budget is reported in every response.
ex:meteredService a sd:Service ;
  sd:endpoint <https://example.org/sparql/metered> ;
  vord:hasRestriction ex:usageBudget .

ex:meteredUnits a vord:CostModel ;
  rdfs:label "Metered usage units, version 1"@en ;
  dcterms:description "A request costs 1 unit, plus 1 unit if it is an aggregate query, plus 1 unit per full 100 result rows."@en .

ex:usageBudget a vord:Restriction, vord:CostModelRestriction ;
  vord:metric vord:costUnitsPerWindow ;
  vord:maxValue "600"^^xsd:integer ;
  vord:burstValue "200"^^xsd:integer ;
  vord:windowDuration "PT1M"^^xsd:duration ;
  vord:unit unit:ONE ;
  vord:costModel ex:meteredUnits ;
  vord:hasScope vord:PerClientIP ;
  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "429"^^xsd:integer ;
  vord:httpSignalHeader ex:x-ratelimit-remaining .

# 2. Identified access, as Wikimedia's User-Agent policy requires: every request must carry a User-Agent that names
#    the client and gives a contact. The rate limit is counted per identity.

  vord:hasRestriction ex:userAgentContact, ex:ratePerUser .

  vord:identificationFormat vord:ProductWithContact ;
  vord:hasScope vord:PerRequest ;
  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "403"^^xsd:integer .

ex:ratePerUser a vord:Restriction, vord:RateRestriction ;
  vord:metric vord:requestsPerWindow ;
  vord:maxValue "20"^^xsd:integer ;
  vord:windowDuration "PT2S"^^xsd:duration ;
  vord:unit unit:COUNT ;
  vord:hasScope vord:PerUser ;
  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "429"^^xsd:integer ;

  vord:metric vord:requestsPerWindow ;

  vord:windowDuration "PT10S"^^xsd:duration ;
  vord:unit unit:COUNT ;
  vord:hasScope vord:PerClientIP ;
  vord:enforcement vord:ThrottleResponse ;
  vord:hardRestriction "true"^^xsd:boolean .

  vord:maxValue "3"^^xsd:integer ;
  vord:unit unit:COUNT ;
  vord:hasScope vord:PerClientIP ;
  vord:enforcement vord:DegradeQuality ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "200"^^xsd:integer ;

  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;

Security and Privacy Considerations

VoRD descriptions can reveal operational thresholds. Publishers should avoid exposing sensitive internal capacity, infrastructure topology, or abuse-detection details that would make it easier to attack a service. Publishing conservative public thresholds is often preferable to publishing exact internal limits.

Scopes such as vord:PerUser, vord:PerAPIKey, or custom identity scopes describe how traffic is grouped; they should not disclose actual user identifiers, API keys, IP addresses, or other personal data.

An identification requirement makes clients disclose personal data, such as an email address, to the endpoint. Publishers should require identification only when they need it, for example to contact or throttle abusive clients, and should accept role or project addresses rather than personal ones. Consumers should send identification only to endpoints whose description requires it.

Penalties are part of abuse detection. Publishers should not reveal more of their abuse-detection rules than clients need to stay within them; publishing conservative penalty values is sufficient.

Maintainer Checklist

  • Does the service description contain an sd:Service and the correct sd:endpoint?
  • Is every operationally meaningful public limit represented by a separate vord:Restriction?
  • Does every restriction have exactly one metric, maximum value, scope, enforcement mode, and hard/advisory boolean?
  • Are units and window durations explicit where clients need them?
  • Are HTTP status codes and retry headers represented when they are part of real endpoint behavior?
  • Are custom metrics and scopes typed and labelled?
  • If clients must identify themselves, is the requirement published as a vord:IdentificationRestriction, and can the service description be retrieved without identification?
  • If the endpoint refuses some ways of sending a query, such as POST, does a vord:RequestMethodRestriction list the ways it accepts?
  • For usage budgets, is the cost model described, and is the remaining budget signalled in a response header?
  • Are budgets of processing time and limits on failed requests published with vord:evaluationTimePerWindow and vord:failedRequestsPerWindow, rather than as request rates?
  • If violations lead to temporary blocks, are vord:penaltyThreshold and vord:penaltyDuration stated, or vord:penalized when their values are not published?
  • Does the RDF pass the VoRD SHACL validation profile?
  • Is the published RDF updated whenever the deployed endpoint policy changes?
